 StockTrader 量化系统缺陷分析                                                                                          
  一、回测引擎 — 最致命的 bug                                                                                            esc to interrupt

  ★ Insight ─────────────────────────────────────
  量化系统中，回测引擎的正确性是一切的基石。一个看似微小的 bug（比如用 unrealized_pnl
  代替组合回撤）会导致所有回测结果失真，进而误导模型选择和参数优化。
  ─────────────────────────────────────────────────

  1.1 回撤计算张冠李戴 (layers/risk/risk_engine.py:103)

  dd_value = unrealized_pnl  # 简化; 实际应从外部传入 portfolio_drawdown

  这行代码用单笔持仓的浮亏代替了组合层面的最大回撤。后果：
  - 回撤约束形同虚设（单笔浮亏 -3% 时组合可能已经回撤 -30%）
  - 动态降仓逻辑永远不会在正确的时机触发
  - 所有 full 模式（三层管道）的回测结果都不可信

  1.2 RL 环境与回测引擎的 observation 不一致

  对比两个 _get_observation / _build_rl_obs:

  ┌─────────┬────────────────────────────────┬───────────────────────────┐
  │  维度   │      ExecutionEnv (训练)       │   BacktestEngine (推理)   │
  ├─────────┼────────────────────────────────┼───────────────────────────┤
  │ core[7] │ trade_count/10                 │ recent_action（永远是 0） │
  ├─────────┼────────────────────────────────┼───────────────────────────┤
  │ core[8] │ balance/initial_balance        │ need_trade flag           │
  ├─────────┼────────────────────────────────┼───────────────────────────┤
  │ history │ pos/signal/target/exec 各 5 天 │ 全 0 填充                 │
  ├─────────┼────────────────────────────────┼───────────────────────────┤
  │ aux     │ 仓位利用率/份额/净值等         │ 完全不同的语义            │
  └─────────┴────────────────────────────────┴───────────────────────────┘

  训练和推理用的是两个不同的 observation builder。 这导致 RL 模型学到的策略在推理时完全失效。

  1.3 止损后再入场逻辑有漏洞

  elif self._stop_loss_triggered:
      pos *= 0.5  # 重新入场减半
      self._stop_loss_triggered = False

  这里把止损标志重置为 False，但设置 _stop_loss_triggered = True 的条件（第 88 行）要求 current_position !=
  0。下一次循环中 current_pos 可能仍非零（如果止损卖出没有全部执行），导致标志反复翻转。

  二、数据层 — 系统性偏差

  2.1 存活者偏差

  你的股票列表只有目前还活着的标的（AAPL、NVDA、000568.SZ 等）。回测时如果选 2015-2026
  的历史区间，系统会自动忽略那些在这个区间内退市的股票。 这意味着：
  - 所有回测收益被高估
  - 信号 IC 被高估
  - 真正量化基金的数据集必须包含退市股的历史数据（point-in-time database）

  2.2 复权处理缺失

  yfinance 默认返回的是未复权价格。分红、拆股会在 OHLCV
  数据中产生跳跃，破坏所有技术指标的计算。你需要在数据拉取后做前复权或后复权处理。

  2.3 停牌/涨跌停无处理

  A 股有涨跌停限制，你的系统完全没有处理。停牌日数据中会出现连续相同的价格，导致波动率被严重低估、技术指标失真。

  三、信号层 — 方法论缺陷

  ★ Insight ─────────────────────────────────────
  量化信号研究有一条铁律：单一标的 + 技术指标 + 机器学习 ≠ 可交易的 Alpha。真正能持续产生超额收益的因子通常来自：基本面
  数据的非线性组合、另类数据的信号提取、或者行为金融学偏差的系统性利用。
  ─────────────────────────────────────────────────

  3.1 特征空间狭隘

  全部 50+ 特征都是价格/成交量的衍生指标。缺失的关键维度：

  ┌────────────────────────────────────┬────────────────────────────────────┐
  │              缺失维度              │             为什么重要             │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ 基本面因子 (PE/PB/ROE/利润率)      │ 估值驱动的中长期 Alpha 来源        │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ 行业/板块信息                      │ 行业中性化是所有量化基金的基础操作 │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ 市场微观结构 (买卖价差/订单簿深度) │ 高频/日内策略的核心输入            │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ 宏观经济指标 (利率/汇率/VIX)       │ 宏观 regime 切换的信号             │
  ├────────────────────────────────────┼────────────────────────────────────┤
  │ 资金流向                           │ 主力资金和散户资金的博弈信息       │
  └────────────────────────────────────┴────────────────────────────────────┘

  3.2 标签构建过于简单

  # label_builder.py — 直接用未来 N 日收益率
  labels = close.pct_change(horizon).shift(-horizon)

  问题：
  - 收益率分布的厚尾特性没有被处理（应该做 winsorization）
  - 没有正交化（剔除市场/行业/风格因子后才是纯 Alpha）
  - 分类标签的阈值是固定的，没有考虑波动率 regime

  3.3 模型评估缺少最关键指标

  你的 AlphaEvaluator 有 IC 和 RankIC，但缺少：

  - 分层回测收益（quantile 分析有了，但没有分层回测的多空组合净值曲线）
  - 因子拥挤度（信号自相关、因子波动率）
  - 换手率成本调整后的 IC（高换手的信号可能真实收益为负）
  - Fama-MacBeth 回归（控制其他因子后的边际贡献）

  ---
  四、风控层 — 教科书式但不可用

  4.1 止损阈值是静态的

  self.stop_loss = -0.05  # 固定 -5%

  真正的量化基金不会用固定百分比止损。应该使用 ATR trailing stop 或 波动率自适应止损。高波动率环境下的 -5%
  可能只是噪声，低波动率下 -5% 则太宽松。

  4.2 流动性约束只检查不拒绝

  LiquidityConstraints 限制了单次交易的 ADV 占比，但没有做更细粒度的处理：
  - 没有 TWAP/VWAP 执行算法模拟
  - 没有考虑不同时段流动性差异（开盘/收盘流动性好，午间差）
  - 没有暗池/大宗交易的考虑

  4.3 缺少的关键风控

  ┌──────────────────┬────────────────────────────────────┐
  │      缺失项      │                风险                │
  ├──────────────────┼────────────────────────────────────┤
  │ 行业集中度限制   │ 看似分散的持仓可能集中在同一行业   │
  ├──────────────────┼────────────────────────────────────┤
  │ 因子暴露限制     │ 无意的动量/价值/规模因子暴露       │
  ├──────────────────┼────────────────────────────────────┤
  │ 相关性崩盘保护   │ 危机时所有资产相关性趋近于 1       │
  ├──────────────────┼────────────────────────────────────┤
  │ 最大回撤时间限制 │ 回撤持续时间过长的退出机制         │
  ├──────────────────┼────────────────────────────────────┤
  │ 凯利准则仓位管理 │ 当前 all-in 式仓位完全无视凯利公式 │
  └──────────────────┴────────────────────────────────────┘

  五、RL 层的设计问题

  5.1 训练时 target 未经风控

  # run_pipeline.py:159
  target_positions=np.clip(test_signals[:len(test_prices)], -1, 1),

  RL 训练时接收的是原始信号映射的 target。但在回测 full 模式中，RL 接收的 target 是经过风控层处理后的。RL
  模型学的是"如何跟随原始信号"，实际使用时面对的却是"如何跟随风控后的信号"——分布完全不同。

  5.2 100K timesteps 远远不够

  金融 RL 的样本效率极低。100K steps 对应约 400 年的日线数据（假设 252 个交易日/年）。实际上模型完全没收敛。

  5.3 奖励函数中的问题

  reward = np.clip(portfolio_return - λ1*cost - λ2*turnover - λ3*drawdown, -10.0, 10.0)

  - portfolio_return 是单步收益（约 0.01% 量级），而 cost 可能是 0.1% 量级，尺度不匹配
  - drawdown_penalty 阈值 drawdown_threshold=0.02（2%），RL 可能在 2% 回撤内频繁调仓刷 PnL
  - clip(-10, 10) 会抹掉尾部信号（而金融中最重要的是尾部）

  ---
  六、工程层面的问题

  6.1 零测试

  整个项目没有一行测试代码。量化系统最需要测试的地方（数据完整性、无未来函数、回测引擎逻辑、指标计算）全部靠"目测"验证。

  6.2 双轨系统混乱

  ┌─────────────────────────┬────────────────────────┬────────────────────────────┐
  │          v1/v2          │           v3           │            状态            │
  ├─────────────────────────┼────────────────────────┼────────────────────────────┤
  │ predictor.py            │ layers/signals/models/ │ 两个系统独立开发，互不兼容 │
  ├─────────────────────────┼────────────────────────┼────────────────────────────┤
  │ improved_data_engine.py │ layers/data/           │ 功能重叠，数据格式不统一   │
  ├─────────────────────────┼────────────────────────┼────────────────────────────┤
  │ config.json             │ config/*.yaml          │ 两套配置体系并存           │
  └─────────────────────────┴────────────────────────┴────────────────────────────┘

  v3 的 pipeline 可以跑但依赖 v1 的前端展示结果，整体是一个"能演示但不能交易"的状态。

  6.3 Walk-Forward 只定义未使用

  WalkForwardBacktest 是一个完整的实现，但 run_pipeline.py 中即使传了 --walk-forward
  也没有实际调用它。这意味着你没有验证过模型在不同市场环境下的稳定性。

  6.4 没有模型持久化管线

  训练完模型后没有自动保存最优模型、没有模型版本管理、没有 AB 测试框架。你训练了 8
  种模型，但没有一个系统化的方式来管理哪个模型在生产中使用。
